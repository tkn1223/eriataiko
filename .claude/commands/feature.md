# /feature — 機能をひとつ作りきる

依頼: **$ARGUMENTS**

この 4 段を順番にやる。**段を飛ばさない。** 途中で行き詰まったら、次に進まずに人間に聞く。

---

## 段 1 — 仕様を固める（あなた＝メインが opus でやる）

### 1-1. 深掘りが必要か判定する

以下の**どれかに触るなら、必ず深掘りする**（自分で「自明だ」と判断して飛ばさない）:

- `supabase/migrations/` にファイルを足す／既存テーブルの列を変える
- `src/app/api/**` を新しく作る（＝書き込みが増える）
- 画面やタブを新しく足す
- 入場・権限のふるまいを変える

以下なら深掘りは省いてよい:

- 文言・色・余白だけの変更
- バグ修正（再現手順がはっきりしている）
- ふるまいが変わらない整理

**迷ったら深掘りする側に倒す。**

### 1-2. 深掘りのやり方

`grilling` スキルを使う（`Skill` ツールで `grilling`）。ただし聞き方は次を守る:

- **1 問ずつ聞く。** まとめて 3 問投げない
- **選択式にする。** `AskUserQuestion` を使い、おすすめを先頭に置く
- **短く。** 前置きは 2 行まで。表や箇条書きを並べない
- **専門用語を使わない。** 相手はエンジニアではない
  - ✗ RLS / ポリシー / スキーマ / ハイドレーション / ペイロード
  - ○ 「他の人に書き換えられないようにする設定」「表のつくり」
- 用語を出さないと説明できないときは、**一度だけ 1 行で言い換えを添える**

聞くべき中身の優先順:

1. **やらないこと**（これが決まらないと作りすぎる）
2. 画面に何が出て、どこを押すと何が起きるか
3. 誰が使うか（観戦者も見るのか、運営だけか）
4. 数の上限（何コート、何人、何試合）
5. 失敗したときどう見せるか

### 1-3. 承認をもらう

`EnterPlanMode` → 深掘り → `ExitPlanMode` で承認ダイアログを出す。プランには必ず入れる:

- やること / **やらないこと**
- 受け入れ基準（○× で判定できる書き方。段 4 がこれを見る）
- 触るファイル（新規・変更）

**承認されるまでコードを書かない。**

### 1-4. 仕様を残す

承認後、`docs/specs/YYYY-MM-DD-<英小文字の名前>.md` に保存する。書式は `docs/specs/TEMPLATE.md`。

そのあとブランチを切る:

```bash
git switch -c feature/<英小文字の名前>
```

---

## 段 2 — 実装する（`implementer` に任せる。sonnet）

`Agent` ツールで `subagent_type: "implementer"` を呼ぶ。渡すもの:

- 仕様ファイルのパス
- 受け入れ基準
- 触ってよいファイルの範囲

テストを先に書いて赤にしてから実装する（実装エージェント側のルール）。

---

## 段 3 — レビューして直す（`reviewer` に任せる。opus）

`Agent` ツールで `subagent_type: "reviewer"` を呼ぶ。渡すもの:

- 仕様ファイルのパス
- 段 2 が触ったファイルの一覧

レビューして**その場で直す**。直したら触ったファイルの周りだけ再テストする。

---

## 段 4 — 動作確認する（`verifier` に任せる。sonnet）

`Agent` ツールで `subagent_type: "verifier"` を呼ぶ。渡すもの:

- 仕様ファイルのパス（受け入れ基準がここにある）

全テストと画面テストを流し、受け入れ基準を 1 件ずつ ○× で判定させる。

---

## 最後 — まとめて報告する

× が残っていたら **PR を作らずに** 人間に報告する。全部 ○ なら:

```bash
git add -A && git commit   # メッセージは仕様の「やること」から
gh pr create               # 本文に仕様の要約と受け入れ基準の結果
```

報告に必ず含める:

- 何を作ったか（1〜3 行）
- 受け入れ基準の ○×
- 途中で決めたこと・妥協したこと
- 次に人間がやること（環境変数の設定など）

`README.md` の書き換えが必要になったら、忘れずに直す。
