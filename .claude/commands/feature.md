# /feature — 機能をひとつ作りきる

依頼: **$ARGUMENTS**

この 5 段を順番にやる。**段を飛ばさない。** 途中で行き詰まったら、次に進まずに人間に聞く。

---

## 段 0 — 全体像を見せて、どれをやるか選んでもらう

**依頼が空でも、はっきりしていても、必ずここから始める。**
自分の判断で「これのことだろう」と決めて段 1 に進まない。

### 0-1. `docs/roadmap.md` を読む

いま何が残っていて、おすすめの順番と誰がやるかが書いてある。
`README.md` や仕様書ではなく、**まずこれを読む。**

### 0-2. 全体像を 1 画面で見せる

次の 3 つを、**専門用語なしで**短く伝える。

1. **いまアプリ全体がどこまでできているか**（`docs/roadmap.md` の「いまの状態」）
2. **いま動いている PR があれば、それが何か**
3. **残っていること**を、おすすめの順番で

### 0-3. どれをやるか選んでもらう

`AskUserQuestion` で選ばせる。**おすすめを先頭に置く。**

`docs/roadmap.md` は **1 行 = PR 1 本**になるように割ってある。
**選ばせるのは「行」1 つ。** 「1 をやる」ではなく「1-a をやる」。
まとめて 2 行やらない。大きいと、レビューで戻ったとき全部やり直しになる。

例:

```
いま残っているのは 5 つ、細かくは 11 本です。おすすめは 1-a です。

1-a. 結果LIVE を DB から読む（見本データをやめる）  ← 当日これが無いと得点が残らない
1-b. ＋ − を押したら保存する
1-c. 他の人の得点をその場で映す
2-a. 進行表を DB から読む
3-a. 勝敗と順位の計算を作る（画面は触らない）
```

**上から順が原則。** 飛ばしたいと言われたら、なぜ飛ばすかを聞いてから進む。
1-a を飛ばして 1-b はできない（読めていないものは保存できない）。

**依頼（`$ARGUMENTS`）が既にどれかに当たるときも、必ず聞く。**
「ご依頼はこれのことですね」と確かめる形でよい。取り違えたまま進むほうが高い。

`docs/roadmap.md` に無いことを頼まれたら、**それが本当に今やることか**を確かめる。
残っていることより先にやる理由があるなら、それを聞いてから進む。

### 0-4. 前提を確かめる

選ばれたものに、`docs/roadmap.md` の「決めていないこと」が絡んでいないか見る。
**絡んでいたら、先にそれを決めてもらう。** 決めずに進むと作り直しになる。

## 段 1 — 仕様を固める（あなた＝メインが opus でやる）

### 1-0. 過去に決めたことを読む（**飛ばさない**）

**このリポジトリは「なぜそうしたか」を書き残している。** 読まずに実装に入ると、
決定と逆のものを作り込んでから気づくことになる（実際に 1,200 行できてから気づいた）。

触る場所ごとに、**最低これだけ**読む。

| 触るもの | 読むもの |
| --- | --- |
| どれでも | `docs/roadmap.md` |
| 得点・試合の終了 | `docs/specs/2026-08-29-score-input-backend.md` の「決めたこと」「やらないこと」「フロントに渡すこと」 |
| 表（テーブル） | 該当する `supabase/migrations/*.sql` の**冒頭コメント** |
| 計算を足す | `src/domain/` に**同じことをする関数・型が既に無いか**（`GameScore` `playedGameScores` など） |

読んだうえで、**過去の決定と違うことをするなら、実装前に人に確認する。**
勝手に覆さない。覆すなら、なぜ覆すかを仕様書に書く。

### 1-1. 深掘りが必要か判定する

以下の**どれかに触るなら、必ず深掘りする**（自分で「自明だ」と判断して飛ばさない）:

- `supabase/migrations/` にファイルを足す／既存テーブルの列を変える
- `src/app/api/**` を新しく作る（＝書き込みが増える）
- 画面やタブを新しく足す
- 入場・権限のふるまいを変える

以下なら深掘りは省いてよい:

- 文言・色・余白だけの変更
- バグ修正（再現手順がはっきりしている）
- ふるまいが変わらない整理

**迷ったら深掘りする側に倒す。**

### 1-2. 深掘りのやり方

`grilling` スキルを使う（`Skill` ツールで `grilling`）。ただし聞き方は次を守る:

- **1 問ずつ聞く。** まとめて 3 問投げない
- **選択式にする。** `AskUserQuestion` を使い、おすすめを先頭に置く
- **短く。** 前置きは 2 行まで。表や箇条書きを並べない
- **専門用語を使わない。** 相手はエンジニアではない
  - ✗ RLS / ポリシー / スキーマ / ハイドレーション / ペイロード
  - ○ 「他の人に書き換えられないようにする設定」「表のつくり」
- 用語を出さないと説明できないときは、**一度だけ 1 行で言い換えを添える**

聞くべき中身の優先順:

1. **やらないこと**（これが決まらないと作りすぎる）
2. 画面に何が出て、どこを押すと何が起きるか
3. 誰が使うか（観戦者も見るのか、運営だけか）
4. 数の上限（何コート、何人、何試合）
5. 失敗したときどう見せるか

### 1-3. 承認をもらう

`EnterPlanMode` → 深掘り → `ExitPlanMode` で承認ダイアログを出す。プランには必ず入れる:

- やること / **やらないこと**
- 受け入れ基準（○× で判定できる書き方。段 4 がこれを見る）
- 触るファイル（新規・変更）

**承認されるまでコードを書かない。**

### 1-4. 仕様を残す

承認後、`docs/specs/YYYY-MM-DD-<英小文字の名前>.md` に保存する。書式は `docs/specs/TEMPLATE.md`。

そのあとブランチを切る。**枝は必ず `develop` から切る**（`main` は本番なので触らない）:

```bash
git switch develop && git pull
git switch -c feature/<英小文字の名前>
```

## 段 2 — 実装する（`implementer` に任せる。sonnet）

`Agent` ツールで `subagent_type: "implementer"` を呼ぶ。渡すもの:

- 仕様ファイルのパス
- 受け入れ基準
- 触ってよいファイルの範囲

テストを先に書いて赤にしてから実装する（実装エージェント側のルール）。

---

## 段 3 — レビューして直す（`reviewer` に任せる。opus）

`Agent` ツールで `subagent_type: "reviewer"` を呼ぶ。渡すもの:

- 仕様ファイルのパス
- 段 2 が触ったファイルの一覧

レビューして**その場で直す**。直したら触ったファイルの周りだけ再テストする。

---

## 段 4 — 動作確認する（`verifier` に任せる。sonnet）

`Agent` ツールで `subagent_type: "verifier"` を呼ぶ。渡すもの:

- 仕様ファイルのパス（受け入れ基準がここにある）

全テストと画面テストを流し、受け入れ基準を 1 件ずつ ○× で判定させる。

---

## 最後 — まとめて報告する

× が残っていたら **PR を作らずに** 人間に報告する。全部 ○ なら:

```bash
git branch --show-current                    # 意図した枝にいるか確認（必須）
git log origin/develop..HEAD --oneline       # develop に対して何が新規か確認（必須）

git add -A && git commit                     # メッセージは仕様の「やること」から
gh pr create --base develop                  # 本文に仕様の要約と受け入れ基準の結果
```

**宛先は必ず `develop`。** `main` は本番なので、ここから PR を出さない。
PR を作るとテストが自動で走る（約 5 分）。緑になってからマージする。

**マージしても公開されない。** 公開は人が Actions の「公開する」を押したときだけ起きる。
勝手に公開しない。報告の「次に人間がやること」に、公開が必要なら書き添える。

報告に必ず含める:

- 何を作ったか（1〜3 行）
- 受け入れ基準の ○×
- 途中で決めたこと・妥協したこと
- 次に人間がやること（環境変数の設定、本番に出すなら `develop` → `main` の PR など）

`README.md` の書き換えが必要になったら、忘れずに直す。
