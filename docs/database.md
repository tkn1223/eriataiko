# データベースの決まり

## 本番は 1 つだけ。確認用と共有している

無料プランなのでデータベースは 1 つです。**本番のサイトと確認用のサイトが、同じデータベースを読み書きします。**

つまり**確認用のサイトで得点を入れると、本番のデータが変わります。**

合言葉は本番と確認用で別にしてあるので、他人が入ることはありません。ただし自分が確認用を触るときは、
本番のデータを触っていることになります。

大会が近づいたら分けるかどうかを決めます（無料枠は 2 つまで作れる）。それまでは 1 つで進めます。

---

## 白紙に戻す

```bash
npx supabase db reset --linked
```

全部消して `supabase/migrations/` から作り直します。表は残り、中身が空になります。

### 戻す手段はありません

**無料プランには自動バックアップも巻き戻しもありません**（Pro 以上の機能）。
一度消したら終わりです。

### だから `package.json` には入れていない

`npm run db:reset` は**手元の**データベース用です。本番を消すコマンドは、
打ちやすくすると事故るので、あえてショートカットを作っていません。
消すときは上の長いコマンドを毎回手で打ってください。`--linked` が「本番」の意味です。

### 絶対に守る線

**大会当日と前日は `--linked` を打たない。** 消えたデータは戻りません。

それまでに、次のどちらかを決めておくこと。

- 表を CSV に書き出しておく（無料でできる）
- 当日だけ Pro プラン（$25/月）にする。翌日下げれば 1 か月分

## 本番に流す（マイグレーション）

表を足したり変えたりしたら、**最後に人が本番へ流します。** ここだけは自動になっていません。

### 仕組み

`supabase/migrations/` の中の**日付が付いたファイル**を、古い順に流していきます。
どこまで流したかはデータベース自身が覚えていて、**まだ流していないぶんだけ**が流れます。

```
supabase/migrations/
  20260811000000_baseline.sql            ← 流し済み
  20260820000000_competition_tables.sql  ← まだ
```

**一度流したファイルは、二度と編集しないこと。** 手元と本番で中身が食い違い、
どちらが正しいか分からなくなります。変えたいときは**新しいファイルを足します**。

### 手順

**1. いま何がずれているか見る**

```bash
npx supabase migration list --linked
```

左が手元、右が本番。右が空の行が「これから流れるもの」です。

**2. 流さずに、何が流れるかだけ見る**

```bash
npx supabase db push --dry-run
```

`Would push these migrations:` に出たファイル名が、あなたの意図と合っているか確かめます。
**身に覚えのないファイルが並んでいたら、そこで止まること。**

**3. ファイルの中身を目で読む**

流すファイルを開いて、`drop` や `delete` が入っていないか見ます。
**追加だけなら安全。何かを消す行があれば、消えるデータが何かを確かめてから。**

**4. 流す**

```bash
npm run db:push
```

**5. 揃ったことを確認する**

```bash
npx supabase migration list --linked
```

左右が同じ並びになっていれば成功です。

**6. アプリを公開する**

**表を足しただけでは画面は変わりません。** 新しい表を使うコードがあるなら、
Actions の「公開する」を押して初めて反映されます。順番は**先に表、あとからコード**。
逆にすると、コードが「まだ無い表」を読みに行って本番が壊れます。

### やってはいけないこと

| コマンド | なぜ危ないか |
| --- | --- |
| `supabase db reset --linked` | **本番を白紙に戻す。** 戻す手段は無い |
| `supabase db push --include-seed` | 開発用のサンプルデータ（架空の選手）が**本番に入る** |
| 流し済みファイルの編集 | 手元と本番が食い違う。誰も気づけない |

どれも `package.json` には入れていません。**ショートカットを作らないこと。**

### いつ流すか

- **大会当日と前日は流さない。** 失敗したときに直す時間がない
- 画面をつなぐ**直前**に流す（早く流しても、使う表が増えるだけ）
- 流す前に `--dry-run` を人に見せて、確認を取る

### 開発用のサンプルデータは本番に行かない

`supabase/seed.sql`（架空の 4 チーム・16 人）は**手元専用**です。
`npm run db:push` では流れません（`--dry-run` の結果の `seeds` が空であることで確かめられます）。
手元に入るのは `npm run db:reset` のときだけです。

## 手元で流す

手元は壊しても痛くないので、**作り直すのが確実**です。

```bash
npm run db:reset      # 作り直して全部流し、サンプルも入れる（ふだんはこれ）
npm run db:types      # 表の形が変わったら必ず。src/types/database.ts を再生成
```

入れたデータを消したくないときだけ、**未実行のぶんだけ**流せます。

```bash
npx supabase migration up
```

| やりたいこと | コマンド |
| --- | --- |
| まっさらから作り直す | `npm run db:reset` |
| 表だけ足す（データは残す） | `npx supabase migration up` |
| 本番へ流す | `npm run db:push` |

## 表を足すとき

手順は `AGENTS.md` の「スキーマ変更の手順」。**`grant` の 2 行を必ず書く**こと。

この Supabase プロジェクトは「新しいテーブルを自動的に公開する」を**オフ**で作ってあります。
つまり `grant` を書き忘れると、本番だけ `permission denied` で失敗します
（手元は既定で公開されるので通ってしまう）。

自動公開をオフにしたのは、**書き忘れたときに黙って読める状態になるより、
はっきり失敗するほうが安全**だからです。静かに漏れるのが一番困ります。

「自動 RLS」は**オン**です。表を足せば読み書きの制限が自動でかかります。

## いまある表

### 大会のデータ（12 表）

```
competitions  大会 ──┬── divisions   部（1部 / 2部 / 3部）
                     ├── teams       チーム
                     ├── participants  参加（人 × 大会）
                     └── stages      予選リーグ / 決勝トーナメント
                           ├── match_settings  段 × 部ごとの決めごと
                           └── matchups        対戦（チームA 対 チームB）
                                 └── matches      試合
                                       ├── match_players  出場者（片側 2 人）
                                       └── game_scores    ゲームごとの得点

players  人（大会をまたぐ。番号で見分ける）── participants から参照
```

| 表 | 中身 | 誰が読めるか | 誰が書けるか |
| --- | --- | --- | --- |
| `competitions` | 大会。`is_current` が true の 1 件が「いまの大会」 | 誰でも | サーバーだけ |
| `divisions` | 部。名前と並び順だけ | 誰でも | サーバーだけ |
| `teams` | チーム。`team_number` から画面の色を引く | 誰でも | サーバーだけ |
| `players` | 人。**番号で見分ける** | 誰でも | サーバーだけ |
| `participants` | 参加（人 × 大会）。**ここに行がある人 = 得点を入れられる人** | 誰でも | サーバーだけ |
| `stages` | 予選リーグ / 決勝トーナメント | 誰でも | サーバーだけ |
| `match_settings` | 段 × 部ごとの決めごと。いまは最大ゲーム数だけ | 誰でも | サーバーだけ |
| `matchups` | 対戦。決勝は「予選1位」の空枠で先に作れる | 誰でも | サーバーだけ |
| `matches` | 試合。**何点先取かは持たない**（下を読むこと） | 誰でも | サーバーだけ |
| `match_players` | 出場者。ダブルスなので片側 2 行 | 誰でも | サーバーだけ |
| `game_scores` | ゲームごとの得点。「＋1」のたびに更新 | 誰でも | サーバーだけ |
| `write_logs` | 誰が何をしたかの記録 | **誰も読めない** | サーバーだけ |

本番で実際に測って、この表のとおりになっていることを確認済みです。
確認のしかたは `tests/rls.test.ts` と同じで、読み取りは通り、書き込みは 401 で拒否されます。

## 大会のデータで、知らないと困ること

### 人は「番号」で見分ける。名前では見分けられない

名前はニックネームなので、**同じ「たろう」が何人もいます。** `players.player_number` が
運営のふる通し番号で、人を特定できる唯一の手がかりです。画面に出すときも
「たろう #12」のように番号を添えてください。

番号は**運営が決めて登録します**（アプリは自動で採番しません）。紙の名簿にも同じ番号を書いておくと、
当日「自分が何番か分からない」が起きません。

### `side_a` / `side_b` は「コートの左右」ではありません

対戦や試合には必ず 2 つの側があり、`side_a` / `side_b` と呼んでいます。
**A がどちらのチームかは `matchups.side_a_team_id` ただ 1 か所で決まります。**

コートの左右とも、画面の左右とも関係ありません。理由は 2 つ。

- バドミントンは **1 ゲームごとにコートを入れ替えます**（第 3 ゲームは 11 点でも入れ替え）。
  「左のペア」は 1 分後には右にいます
- 星取表は同じ対戦を 2 つのマスに出します。片方では行、もう片方では列に同じチームが来ます

`side_a_score` は「A 側の得点」であって「左の得点」ではありません。
画面にどちら側を左に出すかは、画面が自由に決めてよいところです。

### 「何ゲームやるか」は持つ。「何点先取か」は持たない

紛らわしいので、はっきり分けて書きます。

| | 持つか | どこ |
| --- | --- | --- |
| 最大何ゲームやるか | **持つ** | `match_settings.max_game_count` → `matches.max_game_count` にコピー |
| 何点先取か | **持たない** | どこにも無い |

ゲーム数を持つのは、**試合を終わらせる処理に要るから**です。得点入力の画面は
`matches.max_game_count` の数だけゲームの枠を並べます。

`match_settings` は「段 × 部」ごとの決めごと（「予選リーグの 1 部は 1 ゲーム」など）で、
そこから試合へコピーします。コピーするのは、当日 1 試合だけ変えたくなったときに
その試合だけ直せるようにするためです。

### 保存していないもの（計算で出すもの）

| 出すもの | どこから |
| --- | --- |
| 試合の勝敗 | `game_scores` の得点と `matches.ending` |
| 対戦（matchup）の勝敗 | その中の試合の勝敗 |
| 順位表 | 勝敗 → ゲーム → 得失点 の順 |

**列を足して保存しないでください。** 得点を直したときに食い違い、どちらが正しいか
分からなくなります。

### 「何点先取」を持たない理由

**勝敗の判定に要らないからです。**

- ゲームの勝ち = **点が多いほう**
- 試合の勝ち = ゲームを多く取ったほう

実際の大会は「1部は 21,21,11 / 2部は 15,15,5」のようにゲームごとに点数が違い、
持たせると**試合の行ごとに点数を書く設定作業**が増えます。これまでも人の目で
確かめてきた箇所なので、設定を足さないほうを選びました。

そのぶん **「終了」は自動になりません。人が「確定」を押したときに終了**になります。
誤入力（21 のつもりで 121）は止まりませんが、あとから直せます。

### 大会を消すと、中身も全部消えます

`competitions` の行を消すと、部・チーム・参加・対戦・試合・出場者・得点まで
連鎖して消えます。**戻す手段はありません**（このページの上のほうを読んでください）。

### 出場者は「片側ちょうど 2 人」をデータベースでは強制していません

行を 1 つずつ入れる都合で、1 人目を入れた瞬間に違反になってしまうためです。
**2 人そろっているかは、取り込みと書き込み API の側で確かめてください。**
