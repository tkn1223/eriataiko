# 当日バックアップ（Google スプレッドシート）の準備

大会当日（2027-01-22）の 10:00〜15:00、15 分おきに全データを自動で
Google スプレッドシートに書き出す仕組みの準備です。エンジニアでなくても、
このページの手順どおりに進めれば設定できます。

準備は次の 5 つです。順番にやってください。

1. Google 側でロボット用のアカウント（サービスアカウント）を作る
2. バックアップ先のスプレッドシートを作る
3. **そのスプレッドシートを、ロボット用のアカウントが編集できるようにする（一番の罠）**
4. アプリ（Vercel）に必要な値を設定する
5. GitHub に秘密のパスワードを設定する

---

## 1. ロボット用の Google アカウント（サービスアカウント）を作る

「サービスアカウント」とは、人間ではなくプログラムが使うための Google アカウントです。
このアプリがスプレッドシートに書き込むときに、これを使ってログインします。

1. https://console.cloud.google.com/ を開く（Google アカウントでログイン）
2. 画面上部でプロジェクトを新規作成する（名前は何でもよい。例: `eriataiko-backup`）
3. 検索バーで「Google Sheets API」を探して開き、**有効にする**ボタンを押す
4. 検索バーで「認証情報」を探して開く
5. 「認証情報を作成」→「サービスアカウント」を選ぶ
6. 名前を適当に付けて（例: `backup`）作成する。役割（ロール）の設定は**スキップしてよい**
7. 作成したサービスアカウントの一覧から、いま作ったものをクリックする
8. 「キー」タブ →「鍵を追加」→「新しい鍵を作成」→ 形式は **JSON** を選んで作成する
9. `xxxxx.json` という名前のファイルがダウンロードされる。**これは 1 回しか作れない。無くさないこと**

このファイルの中に、次の 2 つの値が入っています。あとで使うので、どこにあるか覚えておいてください。

- `"client_email"` の値（`....gserviceaccount.com` で終わるメールアドレス）
- `"private_key"` の値（`-----BEGIN PRIVATE KEY-----` から始まる長い文字列）

---

## 2. バックアップ先のスプレッドシートを作る

1. https://sheets.new を開く（Google スプレッドシートが新規作成される）
2. 分かりやすい名前を付ける（例: `えりあ太鼓 大会バックアップ`）
3. アドレスバーの URL をコピーしておく。次のような形になっています。

   ```
   https://docs.google.com/spreadsheets/d/【この部分】/edit
   ```

   `/d/` と `/edit` の間の文字列（英数字の羅列）を控えておいてください。これが
   「スプレッドシート ID」です。あとで使います。

---

## 3. サービスアカウントを編集者に追加する（★ここが一番の罠★）

**これを忘れると、当日いくら動かしても書き込みが全部失敗します。** サービスアカウントは
「1 で作っただけ」では、どのスプレッドシートも触れません。**このスプレッドシートを編集してよい**
と明示的に許可する必要があります。

1. 2 で作ったスプレッドシートを開く
2. 右上の「共有」ボタンを押す
3. ユーザーやグループを追加の欄に、1 で控えた `client_email` の値
   （`....gserviceaccount.com` のメールアドレス）を貼り付ける
4. 権限が **「編集者」** になっていることを確認する（「閲覧者」だと書き込めない）
5. 「通知」のチェックは外してよい（ロボットにメールは届かない）
6. 「共有」または「送信」を押す

これで、このスプレッドシートだけをロボットが書き換えられるようになりました。

---

## 4. アプリ（Vercel）に環境変数を設定する

`docs/deploy.md` の「2. Vercel 側に環境変数を入れる」と同じ場所（Project Settings >
Environment Variables）に、次の 4 つを追加します。**Production にだけ**設定してください
（このバックアップは本番でしか動かさないため）。

| 名前 | 中身 |
| --- | --- |
| `GOOGLE_SERVICE_ACCOUNT_EMAIL` | 1 で控えた `client_email` の値 |
| `GOOGLE_PRIVATE_KEY` | 1 で控えた `private_key` の値。JSON ファイルをテキストエディタで開き、`"private_key": "..."` の `...` の部分をそのままコピーする（前後の `"` は含めない）。文字の中に `\n` が混ざっていても、そのままで大丈夫（アプリ側で本物の改行に直す処理が入っている） |
| `BACKUP_SPREADSHEET_ID` | 2 で控えたスプレッドシート ID |
| `BACKUP_SECRET` | 次のコマンドで作った、長いランダムな文字列。当日この値を GitHub 側にも設定する |

```bash
openssl rand -base64 32
```

この 4 つは「秘匿（Sensitive）」のままで問題ありません。アプリが動いているときに
サーバーへ渡される値だからです。**ただし `NEXT_PUBLIC_` で始まる値を秘匿にすると本番が壊れます。**
理由と直し方は `docs/deploy.md` の「秘匿（Sensitive）にしてはいけない値がある」を読んでください。

設定したら、Vercel で一度再デプロイしてください（環境変数は再デプロイしないと反映されません）。

---

## 5. GitHub に秘密のパスワードを設定する

`.github/workflows/backup.yml` が、当日 15 分おきにこのアプリの `/api/backup` を叩きます。
そのとき「本物のリクエストである」と確かめるために、4 で作った `BACKUP_SECRET` と
同じ値を GitHub にも登録します。

1. GitHub のリポジトリを開く
2. Settings > Secrets and variables > Actions > Secrets タブ
3. 「New repository secret」
4. 名前: `BACKUP_SECRET`、値: 4 で使ったものと**まったく同じ文字列**

---

## これで当日は自動で動く

上の 5 つが終われば、大会当日（2027-01-22）の 10:00〜15:00 に、GitHub Actions が
15 分おきに自動でスプレッドシートへ新しいタブを作ります。タブの名前は書き込んだ時刻
（例 `10-15`）です。

データが壊れたと思ったら、直前のタブを見て、そこに書かれている内容を手で打ち直してください
（このアプリからスプレッドシートへ書き戻す機能は無いので、あくまで「見て確認する用」です）。

## 手で動かす（いつでもできる）

GitHub の `Actions` → 左の **`当日バックアップ（スプレッドシート）`** → `Run workflow`。

**手で押したときは日付を見ません。** いつ押しても実際に書き出します。次の 2 つのために
そうしています。

- **リハーサル** … 本当に書き込めるか、大会より前に確かめる
- **当日の緊急バックアップ** … 「直す前にいまの状態を残したい」。次の自動実行（最大 15 分後）を待たない

押したあと、スプレッドシートに `HH-mm` のタブが増えていれば成功です。

時計で動く定期実行のほうは、`2027-01-22` 以外の日は何もせず終わります
（cron に年を書けないため、翌年の同じ日付に動くのを止めている）。

---

## ⚠ 定期実行はまだ一度も動いたことがありません

2026-08-13 の時点で、**GitHub の定期実行がこのリポジトリで 1 回も発火していません。**

確かめたこと:

| 調べたこと | 結果 |
| --- | --- |
| ワークフローの状態 | 4 つとも `active` |
| GitHub Actions の障害 | なし |
| cron の書式 | `actionlint` 指摘 0 件 |
| 既定ブランチにファイルがあるか | ある |
| 時間帯もタイムゾーンも外した `*/5 * * * *` で 30 分待つ | **0 回** |

設定の間違いではありません。**リポジトリを作った当日**だったことが原因と思われます
（新しいリポジトリでは定期実行がしばらく動かない例が多く報告されている）。

そのため cron は **UTC で書き直しました。** `timezone: 'Asia/Tokyo'` は新しい機能で、
効いているかを検証できませんでした。効かなければ当日 19:00〜23:45 に動いて全く
役に立ちません。**確実さを取って、昔からある UTC 指定にしています。**

### 当日までに必ずやること

1. **もう一度リハーサルする**（下の手順）。リポジトリが古くなれば動くはず
2. 動かなければ、**GitHub の定期実行に頼るのをやめる**。代わりの案:
   - Supabase の中で定期実行して `/api/backup` を叩く（無料・時刻が正確）
   - 当日 15 分おきに人がボタンを押す（確実だが手間。運営がその場にいるので不可能ではない）
   - Vercel の定期実行（15 分おきは有料プランが必要）

**「たぶん動く」で当日を迎えないこと。** 一発勝負です。

---

## リハーサルをすること（必須）

上の「手で動かす」で**書き込めること**は確かめられます。しかし
**時計で自動起動すること**は別問題で、押すだけでは確かめられません。

タイムゾーン指定（`timezone: 'Asia/Tokyo'`）は GitHub Actions でも新しい機能です。
**大会より前に一度、`.github/workflows/backup.yml` の cron を近い日時に書き換えて、
本当に自動で動くか確認してください。** 一発勝負なので、ここを飛ばすと「動くはずだったのに
1 回も動かなかった」が起こり得ます。確認が終わったら `2027-01-22` に戻すこと。

**定期実行は、既定のブランチ（`main`）に入っているファイルしか動きません。** 枝の上に置いた
ままでは自動実行は 1 回も起きません（手で動かすボタンは使えるので、動くように見えて騙されます）。

## 大会の前に必ず見ること

**公開リポジトリでは、60 日間リポジトリに動きがないと定期実行が自動で止まります。**

作り終わってから当日まで間が空くと、これに引っかかります。止まっていても画面上は
静かなので、**当日まで気づけません。**

大会の 1 週間前に、`Actions` の一覧で `当日バックアップ（スプレッドシート）` が
`active` になっているか見てください。止まっていたら有効に戻します。

```bash
gh workflow list --all
gh workflow enable "当日バックアップ（スプレッドシート）"   # 止まっていたら
```

## うまくいかないとき

### バックアップ API が失敗する（401）

`BACKUP_SECRET` が Vercel と GitHub で食い違っています。両方を見比べてください
（コピペミスで前後に空白が入っていないかも確認）。

### バックアップ API が失敗する（401 以外・500 など）

Vercel の環境変数（4 つ）のどれかが未設定か、間違っています。特に多いのは:

- `GOOGLE_PRIVATE_KEY` の貼り付けミス（`"` を含めてしまった、途中で改行が切れた）
- **3 の「編集者に追加する」を忘れている**（Google 側が「権限がありません」と返す）

### 「手動で動かしたのに何も起きない（けど成功と表示される）」

`.github/workflows/backup.yml` の最初のステップが、今日の日付を確認しています。
`2027-01-22`（日本時間）以外の日に動かすと、わざと何もせず成功で終わる作りになっています
（cron の設定に「年」を書けないため、翌年以降に誤って動かないようにする保険です）。
リハーサルするときは、この日付を一時的に近い日へ書き換えてください。
